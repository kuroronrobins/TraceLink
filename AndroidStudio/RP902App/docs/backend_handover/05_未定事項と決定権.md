# 05 未定事項と決定権

この資料では、未定事項を「サーバー側で決めてよい」「アプリ担当と合意してから決める」「今すぐ決めなくてもよい」に分けます。

## 後回しにすると危険なもの

| 項目 | 区分 | 理由 |
| --- | --- | --- |
| API endpoint / method | 要合意 | アプリ側の本物 upload 実装に必要 |
| request JSON field | 要合意 | field 名や必須/任意がズレると送信できない |
| 成功レスポンスの意味 | 要合意 | アプリが `Upload completed` と表示してよい条件に直結 |
| 冪等性キー | 要合意 | retry で二重保存する危険がある |
| error code / retryable | 要合意 | アプリが再送すべきか判断できない |
| 認証方式 | 要合意 | 本番接続の安全性とアプリ実装に関わる |

## サーバー担当者が任意に決めてよいもの

| 項目 | 補足 |
| --- | --- |
| backend framework | API 契約を満たせば自由 |
| ORM / SQL mapper | PostgreSQL に保存できれば自由 |
| migration tool | 社内標準に合わせてよい |
| DB 内部 primary key | アプリに露出しないなら自由 |
| table / schema の物理名 | API 契約と分離されていれば自由 |
| index / partition / archive 方針 | 性能や運用に合わせてよい |
| audit log の詳細保存形式 | アプリ契約と分ければ自由 |
| master data table 設計 | 業務要件に合わせてよい |

## アプリ担当と相談して決めるべきもの

| 項目 | 論点 |
| --- | --- |
| `deviceId` | 現在は仮固定値。端末 ID、ログインユーザー、管理番号のどれを使うか |
| `readerType` | `"RP902"` 固定でよいか、将来 reader 種別を増やすか |
| `readerAddress` を送るか | Bluetooth MAC は個体情報として扱う可能性がある |
| `sessionId` 採番者 | 現在はアプリ。サーバー採番にするなら upload 前後の流れが変わる |
| `idempotencyKey` | `sessionId` と同じにするか、HTTP header を追加するか |
| 空 tags の扱い | 現在アプリは送らない。API でも拒否するか |
| 時刻の扱い | 端末時刻とサーバー時刻を両方保存するか |
| upload 成功時に業務判定も返すか | 初期は保存成功だけでよいか、照合結果まで返すか |

## 今すぐ決めなくてもよいもの

| 項目 | 後でよい理由 |
| --- | --- |
| master data 照合の詳細 | 最小 API は session 保存だけで始められる |
| 管理画面 | 初期 API 保存とは分離できる |
| 高度な検索 API | まず保存と retry の安定化が優先 |
| audit log の長期保管期間 | 運用要件が固まってからでよい |
| PostgreSQL partition | データ量見積もり後でよい |
| 非同期 job queue | 初期は同期保存で十分な可能性が高い |

## サーバー側に任せると危険な部分

以下はサーバー側だけで決めると、アプリ修正や現場運用に影響します。

1. `sessionId` を無視して毎回新規保存する  
   retry で同じ session が重複保存されます。

2. 成功レスポンスの形式を後から大きく変える  
   アプリ側の `UploadResult.Success` 判定が壊れます。

3. validation error と temporary error を区別しない  
   アプリが再送すべき失敗か判断できません。

4. `deviceId` を必須にするが採番方法を決めない  
   現在の仮固定値のまま本番運用に入る危険があります。

5. 時刻をサーバー時刻だけにする  
   現場で実際に読んだ時刻を失う可能性があります。

## 決定会議で確認する質問

- API endpoint は何にするか。
- `sessionId` を冪等性キーとして使ってよいか。
- 同じ `sessionId` で payload が違う場合は `409 Conflict` でよいか。
- 成功レスポンスは `status: accepted` でよいか。
- error response に `retryable` を含めるか。
- 認証方式は何にするか。
- `deviceId` は誰がどう採番するか。
- backend は保存成功だけ返すか、業務判定も返すか。
