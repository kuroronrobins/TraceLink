# 07 実装開始ガイド

この資料は、サーバー担当者が最初に着手する順番を示します。最小構成で始め、アプリ側の本物 upload 実装へつなげやすい流れを優先します。

## 最初に着手すべき順番

1. API request / response の最小契約を合意する。
2. PostgreSQL に `inventory_sessions` と `inventory_tags` を作る。
3. dummy API で request JSON を受けて validation する。
4. `sessionId` の unique 制約と retry 時の動作を実装する。
5. 保存成功時に `status: accepted` を返す。
6. validation error と temporary error の形式を決める。
7. アプリ側で `FakeUploadRepository` から本物 HTTP upload 実装へ差し替える。

## ダミー API で始める場合

最初は DB 保存なしでもよいですが、以下は必ず確認します。

| 確認 | 内容 |
| --- | --- |
| JSON parse | アプリ payload を受け取れるか |
| tags validation | tags が空でないことを確認できるか |
| success response | アプリが success と判断できる形式か |
| error response | アプリが failure と判断できる形式か |
| duplicate simulation | 同じ `sessionId` を複数回送ったときの方針を確認できるか |

## PostgreSQL スキーマ作成の順番

1. UUID を使うなら `pgcrypto` などの extension 方針を決める。
2. `inventory_sessions` を作る。
3. `app_session_id` に unique 制約を付ける。
4. `inventory_tags` を作る。
5. `(inventory_session_id, epc)` に unique 制約を付ける。
6. 必要なら `upload_attempts` を作る。
7. 検索に必要な index を追加する。

## アプリ側の差し替えポイント

| ファイル | 役割 |
| --- | --- |
| `domain/upload/UploadRepository.kt` | upload transport の契約 |
| `data/upload/FakeUploadRepository.kt` | 現在の fake 実装。本物実装の参考 |
| `data/inventory/DefaultInventoryRepository.kt` | `UploadRepository.upload()` を呼ぶ場所 |
| `data/AppContainer.kt` | fake upload を本物 upload 実装へ差し替える場所 |
| `domain/upload/InventoryUploadPayload.kt` | request JSON の元になる model |

本物サーバーに接続するときは、`FakeUploadRepository` を直接改造するより、例えば `HttpUploadRepository` のような別実装を追加して `AppContainer` で差し替える方が安全です。

## ローカル開発でまず確認すべき項目

1. dummy API に `POST` できる。
2. non-empty tags で success になる。
3. empty tags はアプリ側で送られない。ただし API 側でも拒否できる。
4. 同じ `sessionId` の再送が二重保存されない。
5. 同じ `sessionId` で中身が違う場合に検知できる。
6. temporary error でアプリが retry queue に残せる。
7. success で retry queue から消せる。

## 最初の API acceptance checklist

- `sessionId` が必須。
- `sentAtEpochMillis` が必須。
- `deviceId` が必須。ただし本番値は未定。
- `readerType` が必須。
- `tags` は 1 件以上。
- `tags[].epc` は空でない。
- `tags[].readCount` は 1 以上。
- `lastSeenAtEpochMillis >= firstSeenAtEpochMillis`。
- 同じ session 内の EPC 重複は拒否または merge する。
- 同じ `sessionId` retry は success として扱える。
