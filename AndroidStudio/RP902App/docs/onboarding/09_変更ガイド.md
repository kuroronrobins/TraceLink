# 09 変更ガイド

今後よくありそうな変更をどこから始めるか、何を壊しやすいかをまとめます。

## PostgreSQL 実接続を追加したいとき

1. `PostgreSQLAccessContract.md` の View / Function 境界を確認する。
2. `PostgresGateway` の実装を `data` 側に追加する。
3. `ReadResultRepository` の実装で registration function を呼ぶ。
4. `WorkContextRepository`、`RuleRepository`、`EquipmentMasterRepository` の実装を追加する。
5. `AppContainer` で fake 実装から実装へ差し替える。
6. pending write と冪等性のテストを追加する。

注意:

- table 直叩き前提の実装にしない。
- SQL や driver の詳細を UI / ViewModel に出さない。
- 接続失敗は `RegistrationState` と structured log に変換する。

## 端末内判定を追加したいとき

1. `ReadJudgementService` を実装する。
2. 入力は `WorkContext`、`RuleBundle`、`EquipmentSnapshot`、`InventoryTag` に絞る。
3. Android API や PostgreSQL 接続を判定サービスへ入れない。
4. 判定結果を `ReadResultRegistrationBundle` に反映する。
5. 純粋ロジックの単体テストを追加する。

## 新しい reader 実装を追加したいとき

1. `ReaderGateway` を実装する新クラスを `data/reader` 配下へ作る。
2. 必要なら `ReaderGatewayMode` に mode を追加する。
3. `ConfigurableReaderGateway.createGateway()` に切替を追加する。
4. Settings UI に選択肢を追加する。
5. preflight が必要なら `ReaderConnectionPreflight` に追加する。

## pending write を永続化したいとき

1. `PendingWriteQueue` の契約で足りるか確認する。
2. Room などの保存方式を選ぶ。
3. `InMemoryPendingWriteQueue` とは別に新実装を作る。
4. `AppContainer` で差し替える。
5. アプリ再起動後の再実行テストを追加する。

## やってはいけない変更

- Composable から `RP902Reader` や vendor SDK を直接呼ぶ。
- Composable から PostgreSQL 接続実装を直接呼ぶ。
- `InventorySession` に Android API や DB API を入れる。
- `DefaultInventoryRepository` に table 名や SQL を直接埋め込む。
- fake reader default を理由なく real に変える。
- vendor SDK の挙動を推測で説明または実装する。

## 変更前チェックリスト

1. 変更先の責務は合っているか。
2. UI state は domain/data state の projection のままか。
3. vendor 型や DB 実装が UI/domain に漏れていないか。
4. fake mode で動くか。
5. 単体テストできるロジックは domain/data に置いたか。
6. docs の説明とコードが矛盾しないか。
