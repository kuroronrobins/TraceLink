# 08 実機デバッグ手順

この資料は、RP902 実機で問題が起きたときに、どのログを見てどう切り分けるかをまとめたものです。

## まず確認すること

1. Settings で `Real RP902` を選んでいるか。
2. RP902 Bluetooth MAC address が正しいか。今回運用では既定値 `DC:0D:30:DA:0F:3C` が入力済みだが、別リーダーを使う場合は Settings で編集する。
3. Android の Bluetooth が有効か。
4. 必要な runtime permission が許可されているか。
5. Inventory 画面で Reader が `Connected` になっているか。
6. Logs 画面で `Reader` category のログが出ているか。

## 接続できないとき

確認するログ:

- `Gateway mode: RealRp902`
- `Preflight result: blocked`
- `RP902 preflight failed`
- `RP902 connect started`
- `RP902 connect failed before state callback`
- `Vendor callback onReaderStateChanged reached`

切り分け:

| ログの状態 | 見るべき場所 |
| --- | --- |
| `Preflight result: blocked` | Settings の Blocking reasons |
| connect started が出ない | `ConfigurableReaderGateway` の preflight で止まっている |
| connect started は出るが callback なし | Bluetooth pairing、MAC、vendor SDK 側 |
| callback で Error | vendor `ConnectState` / `ResultCode` の内容 |

## Start で落ちるとき

過去に `DisplayOutput` 経路で JNI crash が確認されています。

見るログ:

- `Calling inventory6c(); RP902 DisplayOutput JNI path is suppressed`
- `RP902 DisplayOutput suppressed before vendor JNI`
- `RP902 inventory start threw`

切り分け:

1. `DisplayOutput suppressed` が出ていれば、app 側の抑止は通っています。
2. それでも native crash する場合は、別の vendor JNI 経路の可能性があります。
3. `DisplayTags minimal configuration failed` が出る場合も、inventory は継続する設計です。

触る候補:

- `DisplayOutputSuppressingRp902Reader.kt`
- `RealRp902Gateway.configureMinimalInventoryDisplayPath()`

## タグが読めないとき

今回の実機調査では、Start / Stop command は通るが tag callback が見えないケースがありました。

見るログ:

- `RP902 inventory listener preflight`
- `RP902 UHF listener attached`
- `RP902 inventory listener ready`
- `RP902 sample-backed UHF tuning completed`
- `RP902 select mask clear completed`
- `RP902 inventory6c() returned`
- `First RP902 tag callback reached`
- `Vendor tag callback #...`
- `RP902 stop() returned ... callbacks=... acceptedTags=...`
- `Read EPC ... repositoryAccepted=true`

切り分け:

| 状態 | 推定箇所 |
| --- | --- |
| `callbacks=0` | vendor callback がアプリに届いていない。listener attach、RP902 設定、タグ環境、FW/SDK を疑う |
| callbacks > 0 だが acceptedTags=0 | `Rp902TagEventMapper` で raw EPC が無効扱い |
| acceptedTags > 0 だが `Read EPC` なし | Gateway から Repository への Flow |
| `Read EPC` はあるが UI に出ない | Repository state から ViewModel/UI の投影 |

## Upload が怪しいとき

見るログ:

- `Upload started with ... tags`
- `Upload completed`
- `Upload failed and queued`
- `Retry started for ... queued uploads`
- `Queued upload completed`
- `Queued upload failed`

切り分け:

| 状態 | 見るべき場所 |
| --- | --- |
| Upload ボタンが押せない | `uiState.tags` が空、または `UploadState.Uploading` |
| Upload failed | `FakeUploadRepository` または将来の backend 実装 |
| Retry 件数が減らない | `InMemoryUploadRetryQueue.remove()` または upload result |
| アプリ再起動で queue が消える | 現在は in-memory なので仕様通り |

## ログを見る順番

1. Settings で preflight の表示を確認。
2. Logs で `Reader` category を確認。
3. Start したら `inventory listener` と `inventory6c()` のログを確認。
4. Stop 後に `callbacks` と `acceptedTags` を確認。
5. `Read EPC` が出るか確認。
6. Upload の場合は `Upload` category を確認。

## 追加ログを入れるときの注意

- raw EPC 全文を出す場合は、実データの扱いに注意してください。
- callback 内で重い処理や UI 操作をしないでください。
- vendor callback から例外を外へ漏らすとアプリが落ちる可能性があります。
- ログを増やしすぎると UI 表示や解析が重くなるため、最初の数件と要約を優先してください。
